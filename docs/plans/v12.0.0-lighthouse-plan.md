# Loofi Fedora Tweaks v12.0.0 Plan — "Lighthouse"

## Recommended release direction

**v12.0.0 should be a proactive health, observability, and guided self-healing release.**

v11.0.0 "Harbor" already established the trust foundation: Unified Action Center, daily maintenance diagnostics, rollback-first guidance, Support Bundle v7, release metadata gates, and Fedora KDE 44 as the stable target. v12 should not add another unrelated feature area. It should connect the existing health, maintenance, Action Center, daemon, CLI, and support-bundle systems into one clearer daily workflow:

> "What is wrong with my Fedora system, is it recurring, what is safe to do next, and what changed since last time?"

Suggested codename: **Lighthouse**.

Reason: v11 "Harbor" made actions safer and more inspectable. v12 "Lighthouse" should make the app actively surface system health signals before the user has to hunt for them.

## v12.0.0 release theme

**Theme:** Proactive Fedora health observability and guided daily recovery.

**Focus:** Persisted health snapshots, trend-aware maintenance, recurring problem detection, safer Action Center recommendations, daemon-collected read-only state, Support Bundle v8, stronger RPM/COPR release verification, and Fedora 45 preview refresh.

**One-sentence release note:**

> v12.0.0 "Lighthouse" turns the v11 Action Center and Daily Maintenance system into a proactive health timeline that detects recurring issues, explains safe next steps, and exports better support data without automatically mutating the system.

## Top priority

### 1. Add a persistent "My Fedora Today" health timeline

This should be the main v12 feature.

Current v11 daily maintenance reports are useful but mostly moment-in-time. v12 should persist bounded snapshots and compare them over time.

Add a new core layer:

```text
loofi-fedora-tweaks/core/observability/
  __init__.py
  snapshot.py
  timeline.py
  fingerprints.py
  trends.py
  privacy.py
```

Required model contracts:

- `HealthSnapshot`
  - timestamp
  - app version/codename
  - Fedora target/profile
  - atomic/traditional mode
  - daily maintenance cards
  - Action Center summary
  - failed service fingerprints
  - journal warning fingerprints
  - disk usage summary
  - package manager health summary
  - rollback/snapshot availability
- `HealthTimelineStore`
  - local JSON storage under the existing app data directory pattern
  - bounded retention, default 30 snapshots
  - schema versioning
  - corruption-safe read fallback
  - privacy-safe export mode
- `ProblemFingerprint`
  - stable ID for recurring failed services, repeated journal warnings, DNF lock problems, repo risk patterns, low disk situations, missing rollback tool, and failed Action Center actions
- `MaintenanceTrendAnalyzer`
  - detects new, recurring, resolved, and worsening states
  - produces user-facing summaries and Action Center candidates

Acceptance criteria:

- `DailyMaintenanceService.collect()` can be converted into a `HealthSnapshot` without running mutating commands.
- Repeated failed service across snapshots is detected as recurring.
- Journal warnings are deduplicated by normalized fingerprints, not raw full log lines.
- Snapshot storage never includes raw home paths, emails, hostnames, tokens, API keys, or private file contents.
- Corrupt local snapshot history does not crash GUI, CLI, daemon, or support export.

## Main deliverables

### 2. "My Fedora Today" dashboard route

Add a clearer Home/Maintenance surface that answers:

- current system status
- what changed since last snapshot
- what is recurring
- what is safe to preview
- what requires manual review
- what is not supported on this machine

Recommended UI placement:

- Home card: **My Fedora Today**
- Maintenance subroute: **Health Timeline**
- Diagnostics subroute integration: show snapshot export and fingerprint details
- Action Center integration: show recommended next safe actions from recurring issues

Do not create a completely new top-level sidebar area. Keep the focused v11 navigation model.

### 3. CLI commands for health snapshots and timelines

Add CLI commands without breaking current aliases:

```bash
loofi-fedora-tweaks --cli health snapshot
loofi-fedora-tweaks --cli health timeline --limit 10
loofi-fedora-tweaks --cli maintenance today
loofi-fedora-tweaks --cli maintenance today --json
loofi-fedora-tweaks --cli action-center recommendations
```

JSON output should be stable enough for automation:

```bash
loofi-fedora-tweaks --cli --json maintenance today
loofi-fedora-tweaks --cli --json health timeline --limit 10
```

Acceptance criteria:

- CLI commands work rootless.
- JSON output contains schema/version fields.
- Commands do not require GUI imports.
- Commands have tests for normal, warning, corrupt-history, and empty-history cases.

### 4. Daemon read-only snapshot collection

Use the existing optional daemon mode to collect non-mutating health snapshots.

Scope:

- collect on daemon start
- collect on a conservative interval, e.g. daily
- manual trigger through CLI/API where existing architecture supports it
- no automatic repairs
- no background `dnf upgrade`, `flatpak update`, `fwupdmgr update`, or service restarts

Acceptance criteria:

- Daemon can collect and store snapshots without elevated privileges.
- If commands are missing, the daemon records `unsupported` instead of failing.
- Daemon failures are visible in support bundle and Diagnostics.
- Systemd user unit packaging still works in the optional `daemon` subpackage.

### 5. Action Center v2 recommendations

Build on v11 Action Center instead of replacing it.

Add:

- trend-aware recommendations from health snapshots
- stable dedupe keys so the same recurring issue does not spam the queue
- source metadata like `observability:timeline`, `maintenance:today`, or `readiness:45-preview`
- better grouping: package manager, services, journal, storage, rollback, updates, firmware, Flatpak, security
- clearer `why_this_matters` and `safe_next_step` fields
- exportable recommendation summary for support bundle

Keep strict execution behavior:

- read-only collection is automatic
- mutating actions remain preview-first
- medium/high-risk actions require explicit confirmation
- rollback guidance must be present before risky actions
- no fix-all button

Acceptance criteria:

- Action Center does not enqueue duplicate recurring items across repeated snapshots.
- Medium/high-risk recommendations are blocked without confirmation.
- Manual-only recommendations never run as commands.
- Action history links back to snapshot/fingerprint IDs.

### 6. Support Bundle v8

Add `SupportBundleV8` while preserving the existing import compatibility pattern.

Required additions:

- `support_bundle_version: 8`
- `schema: "12.0.0-lighthouse-support-v8"`
- latest `HealthSnapshot`
- bounded `HealthTimeline`
- recurring problem fingerprints
- Action Center recommendation summary
- daemon snapshot status
- read-only collection errors
- safe GitHub issue text that summarizes recurring problems
- stronger redaction tests for snapshot/timeline content

Compatibility:

- preserve older fields that external consumers might use
- keep compatibility import paths where v5/v6/v7 naming has been intentionally preserved
- do not remove existing support bundle keys during v12

### 7. Fedora 45 preview refresh

Fedora KDE 44 should remain the stable supported target for v12 unless the project intentionally decides to promote Fedora 45 after official release readiness is proven.

For v12, update the existing Fedora 45 preview checks rather than making Fedora 45 the default.

Refresh checks for:

- Python 3.15 / setuptools compatibility
- PyQt6 / Qt packaging compatibility
- DNF5 / PackageKit behavior
- rpm-ostree and Atomic Fedora upgrade path
- Flatpak KDE runtime availability
- Podman 6 compatibility where the existing preview profile already tracks it
- IPv6-mostly NetworkManager behavior where relevant
- RPM/OpenSSL compatibility assumptions
- KDE Plasma session / Wayland assumptions

Acceptance criteria:

- Fedora 45 preview stays non-blocking.
- `--target 45-preview` still works.
- Existing Fedora 44 readiness behavior remains default.
- Support Bundle v8 can include both Fedora 44 current state and Fedora 45 preview planning context.

## Non-goals

Do **not** do these in v12:

- Do not rewrite the whole UI.
- Do not add a new permanent top-level sidebar category.
- Do not promote Fedora 45 to stable unless the release is officially ready and the project deliberately changes support policy.
- Do not add automatic repair/fix-all behavior.
- Do not run package upgrades, service restarts, firmware updates, or cleanup tasks automatically in the daemon.
- Do not lower coverage below 84%.
- Do not claim Flatpak as a stable release channel while its workflow remains non-blocking.
- Do not break existing route IDs, plugin IDs, favorites, settings, or CLI aliases.
- Do not remove older support bundle compatibility fields.

## Done criteria

v12.0.0 is done when:

- `v12.0.0 "Lighthouse"` is the only active roadmap release.
- Version metadata is aligned across runtime, package, AppStream, docs, workflow specs, and release notes.
- Health snapshots persist and survive corrupt local state.
- Maintenance timeline detects new, recurring, resolved, and worsening issues.
- Action Center recommendations are deduped and linked to snapshot/fingerprint IDs.
- Daemon snapshot collection is read-only and rootless.
- Support Bundle v8 includes timeline/recommendation data with redaction guarantees.
- Fedora 44 remains default and Fedora 45 remains preview/advisory.
- README screenshots and user docs match the real UI.
- `just verify` passes.
- `just validate-release` passes.
- `just check-packaging` passes.
- `just release-prep` passes.
- CI passes on `master`.
- RPM artifact installs and smoke tests pass.
- GitHub Release publishes with correct notes and artifacts.
- COPR build is submitted for configured chroots.
